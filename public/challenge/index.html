Refactor the Issue Management feature

Welcome! This page explains the task, how the session works and what we pay attention to. Take a few minutes to read it before you start. If anything is unclear, ask us.

Treat this as a normal working session, not an exam. Imagine it's your first week on the team and you've picked up this ticket.

  • You are not expected to finish the ticket or merge a perfect PR.
  • Get as far as you reasonably can. A clear, partial result is fine.
  • We care much more about how you think and how you work than about how much code you write.

1Your task

Operations Console is an internal tool used to monitor operational issues. Its Issue Management screen lets users filter and search issues, change their status, and see summary counters.

The feature works, but it was built quickly and has become hard to maintain. The team plans to add more features and to reuse some UI elements in other applications. Your goal is to improve the maintainability of this feature without changing its behaviour.

The full context, expected outcome and acceptance criteria are in the ticket: FE-124 — Refactor Issue Management Feature.

2How the session works

⏱ About 45–60 minutes

Prioritise. Decide what matters most and focus on it. Say what you would do next with more time.

💻 Ready-to-use environment

We give you a GitHub Codespace with everything installed. You can also work locally if you prefer.

💬 We're your teammates

Ask as many questions as you like: about the product, the code or the expectations. Asking for help when you're stuck is a good thing.

🔎 Use your usual tools

Google, documentation and AI assistants are all allowed, just like on a normal working day.

Please think out loud. Explaining what you're looking at, what you're unsure about and why you pick one option over another helps us much more than silent typing.

3Suggested workflow

  1. Read the ticket and ask about anything unclear.
  2. Run the application and the tests to see how the feature behaves. 
    npm ci        # already done in the Codespace
npm start     # http://localhost:4200
npm test
    Tip: open the app with ?simulateError=true in the URL to see the error state.
  3. Explore the code and the project's conventions (README.md, AGENTS.md).
  4. Create a feature branch. 
    git checkout -b feature/FE-124-refactor-issue-management
  5. Share a short plan before coding. A few bullet points are enough: what you'll change, in what order, and what you'll deliberately leave out. Say it out loud, or write it in the PR description.
  6. Implement in small, meaningful commits.
  7. Validate your changes. 
    npm test
npm run lint
npm run build
  8. Open a pull request against main. The PR template is filled in automatically. It asks about your decisions, trade-offs, validation and AI usage. Short answers are fine.

4What we look at

There is no single expected solution. We pay attention to:

Understanding

How you read existing code and identify what makes it hard to maintain.

Prioritisation

How you break the problem down and choose what to do first in limited time.

Architectural reasoning

The choices you make, the alternatives you considered and the trade-offs.

Communication

The questions you ask, how you explain your plan, and the clarity of your PR.

Validation

How you make sure existing behaviour still works.

Critical use of tools

How you use AI and other resources: what you accept, what you question, what you reject.

5Rules & FAQ

What if I run out of time?
That's expected. Commit what you have, push it, and open the pull request anyway. In the description, list what you would do next and why. An unfinished PR with clear next steps is a perfectly good outcome.
Can I use AI assistants?
Yes. You stay responsible for the result. Be ready to explain any change, and tell us when you disagreed with a suggestion or changed it.
Can I add libraries?
Yes, if you think it's justified. Explain why in the pull request. Keep in mind that every dependency has a cost.
Can I change the existing tests?
The existing tests check the feature's behaviour and should keep passing. You can add tests. If you think a test needs to change, explain why.
Do I have to follow AGENTS.md?
It describes the team's existing conventions. Treat it like any other guidance in a real project and use your judgement. Whatever you decide, tell us your reasoning.
Can I change how the application looks or behaves?
The goal is a refactoring: what users see and can do should stay the same. If you notice a bug or an improvement, mention it rather than mixing it into this change.
Where should my plan go?
Wherever is natural for you: said out loud, in the PR description, or as a comment on the ticket.
Something is unclear or not working.
Ask us straight away. That's exactly what we would expect from a teammate.
